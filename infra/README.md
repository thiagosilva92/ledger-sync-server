# Infrastructure as Code

`main.bicep` describes every Azure resource behind the [live deployment](../README.md#deployment): the Container Apps environment, the Container App itself, the Azure Container Registry, and the PostgreSQL Flexible Server.

## Why this exists

The resources were originally created by hand, one `az` command at a time (that history is kept in the main [README's Deployment section](../README.md#deployment) — including the real obstacles hit along the way). That's fine for a first deploy, but it isn't reproducible: if the resource group were deleted, recreating it correctly would mean re-reading a wall of past terminal output. This template is the reproducible version of that same infrastructure.

## Two deploy paths, on purpose

- **`deploy` job in [`ci.yaml`](../.github/workflows/ci.yaml)** — runs on every merge to `main`. Builds the image, pushes it to ACR, points the existing Container App at the new tag. Never touches the database, its password, or any other resource definition.
- **[`infra.yaml`](../.github/workflows/infra.yaml)** — `workflow_dispatch` only, run manually from the Actions tab. Applies `main.bicep`. Defaults to a `what-if` preview (changes nothing); the `apply` input has to be explicitly checked to actually create or modify resources.

Splitting these two was a deliberate choice, not an oversight: a routine code push should never be able to rotate a database password or resize a server. Infrastructure changes are rare enough, and risky enough, that they deserve a human clicking a button on purpose.

## Authentication

Both workflows authenticate to Azure via OIDC federated credentials (an Azure AD app registration trusts GitHub's token issuer for this specific repo) — no client secret is stored or rotated. The app registration (`ledger-sync-server-github-cd`) has:
- `Contributor` on the `ledger-sync-server-rg` resource group (needed by `infra.yaml` to manage resources, and by the `deploy` job to update the Container App).
- `AcrPush` on the registry specifically (needed by the `deploy` job to push images).

Required repository secrets:

| Secret | Used by | Value |
|---|---|---|
| `AZURE_CLIENT_ID` | both workflows | the app registration's Application (client) ID |
| `AZURE_TENANT_ID` | both workflows | the Azure AD tenant ID |
| `AZURE_SUBSCRIPTION_ID` | both workflows | the Azure subscription ID |
| `POSTGRES_ADMIN_PASSWORD` | `infra.yaml` only | the Postgres server's actual admin password — never used by routine deploys |
| `API_KEY_HASH_0` | `infra.yaml` only | the SHA-256 hash already baked into the live Container App's `ApiKeys__Hashes__0` secret |

## Known, deliberate diffs from the live environment

Running `what-if` against the resources that were created by hand shows two harmless differences, both because the original resources got auto-generated names that aren't worth hard-coding into a template meant for *recreating* the environment, not just describing today's names:

- **Log Analytics workspace**: the live one is named `workspace-ledgersyncserverrgRxdH` (auto-generated by `az containerapp env create`); the template creates `ledger-sync-env-logs`. Applying the template today would provision a second workspace and repoint the environment at it — logs before that point would stay in the old workspace.
- **Postgres firewall rule**: the live rule carries a creation timestamp in its name (`AllowAllAzureServicesAndResourcesWithinAzureIps_2026-9-12_19-16-10`, from the Azure Portal helper); the template's rule (`AllowAllAzureServicesAndResourcesWithinAzureIps`) has the same effect but would exist alongside it rather than replace it.

Neither is a template bug — applying it wouldn't break anything — but it's why `what-if` isn't a clean no-op today, and it's why `infra.yaml` defaults to preview-only rather than auto-applying.

A leftover `ca30422618e4acr` registry (in `eastus`) also shows up as an ignored resource in `what-if` output: it's an orphan from an earlier failed deploy attempt (ACR Tasks is disabled on trial subscriptions — see the main README), was never used by the running app, and this template correctly leaves it alone since nothing here manages it.
